# OKF — how the vault maps to Google's Open Knowledge Format v0.2

The Open Knowledge Format (OKF) is Google Cloud's open, vendor-neutral specification (v0.1 June 2026, v0.2 July 2026, Apache-2.0, in the `GoogleCloudPlatform/knowledge-catalog` repository) for representing knowledge as **a directory of Markdown files with YAML frontmatter**. It formalises the "LLM wiki" pattern — an agent-maintained, cross-linked Markdown corpus — so that people, agents, search indexes and plain code can read the same files. It is a file format, not a service: no SDK, no registry, no lock-in.

This vault is a conformant OKF bundle. That costs almost nothing and buys interoperability with every agent that speaks OKF.

## Conformance (spec §11) and how the kit enforces it

| Requirement | In the vault | Enforced by |
|---|---|---|
| Every non-reserved `.md` has parseable YAML frontmatter | templates and examples all have it | `kit.py validate`, `tests/test_okf_conformance.py` |
| Every frontmatter has a non-empty `type` | `type` is the first line of every template | same |
| `index.md` follows §8 (no frontmatter except root `okf_version`) | generated by `kit.py index` | same |
| `log.md` follows §9 (`## YYYY-MM-DD` headings, newest first) | `kit.py log "…"` appends correctly | same |

Consumers must tolerate unknown fields and types, broken links and missing optional families, so the vault's own properties (`state`, `health`, `sensitivity`, `meeting_type` …) are fine alongside the OKF ones.

## Field mapping

| OKF v0.2 | Vault | Notes |
|---|---|---|
| `type` (required) | `type` | lower-case kind: `meeting`, `project`, `decision`, `concept`, `runbook`, `spec`, … |
| `title`, `description`, `tags` | same | `description` = one sentence; it drives Bases views and `index.md` |
| `resource` | optional | for notes about a concrete asset (a repo, a dashboard, a service) |
| `generated: { by, at }` | same; templates stamp `human:<you>` + ISO-8601 with offset | v0.1 `timestamp` is superseded; the validator warns if it appears |
| `verified: { by, at }` or list | on decisions and knowledge | derives the **trust tier**: unverified → machine-confirmed → human-reviewed |
| `status` (`draft` · `stable` · `deprecated`) | same, on knowledge notes | absent = stable. Workflow lives in `state` |
| `stale_after` (ISO-8601 instant) | same | the dashboard's *Needs Review* view compares it with today |
| `sources: [{ id, resource, title, author, usage_count, last_modified }]` | same, on knowledge notes | cite in the body with `[^id]` footnotes; `# Citations` lists are v0.1 |
| Attested Computation (`runtime`, `parameters`, `executor`, `attester`) | not used | relevant for metric definitions bound to SQL/dbt; add a `computation` type if you need it |
| Markdown links, bundle-relative or relative | relative markdown links | Obsidian writes them; wikilinks would be invisible to OKF consumers |
| `index.md` per directory | root only | progressive disclosure for agents; regenerate after adding notes |
| `log.md` | root | `kit.py log "message" --kind Creation` |

Actor convention: `human:<id>` for people, `process:<id>` for jobs, `<producer>/<version>` for agents (e.g. `lmstudio/minicpm5-2b`). Only `human:` counts as human-reviewed, so keep it honest — when a model writes a note, put the model in `generated.by`.

## What an agent should do with it

1. Read `index.md` (titles + descriptions) before opening anything — that is the point of progressive disclosure.
2. Prefer `07-knowledge` for facts (they carry `verified`/`stale_after`), `06-decisions` for rationale, `03-projects` for status; the journal is raw material.
3. Treat `status: draft` and past `stale_after` as *lower confidence*, not as errors.
4. When writing: set `generated.by` to itself, never set `verified`, and append to `log.md` — exactly what the kit's MCP bridge and `kit.py log` support.

## Validators

- `uv run kit.py validate --vault <path> --strict` — the kit's validator (Python, no network), also run by `kit.py test`.
- Google's reference validator: `node validator/okf-validate.mjs <bundle>` from a checkout of `GoogleCloudPlatform/knowledge-catalog`. The two agree on §11; the kit additionally checks the ISO-8601-with-offset rule, the actor convention and the `status` vocabulary, and warns on missing descriptions.

## Boundaries

OKF describes knowledge; it does not replace retrieval (qmd), tool access (MCP), permissions, or governance. Nor is it a web or SEO signal — publishing a bundle changes what your agents can rely on, nothing else.
